# 评估：规划模型是否需要"类似 agent 的多轮工作"

> 缘起：故事模型与写后结算模型的输入输出都是定死的，更像"某个 agent 的一部分"而不是独立 agent。那么真正值得讨论的是**规划模型**——它是否需要像 harness 里的 agent 那样多轮工作、逐步逼近结果？
>
> **结论：不需要。** 规划模型的失败模式不是"一轮想不完"，而是"输出没遵守契约"；而契约问题靠**确定性校验**解决，比让模型自我多轮更可靠、更便宜。它当前确实是"某个 agent 的一部分"，这个定位是对的，应该保持。

---

## 一、先把三个模型的分工摆清楚

当前一个回合 = 3 次独立模型调用，构成**一个** agent 循环（而不是三个 agent）：

```
玩家输入 → planner_pre（产出写作契约 JSON）
        → story（只写正文，输入输出都是文本）
        → planner_post（产出状态增量 Patch JSON）
        → 程序提交（唯一写入权威状态的地方）
```

| 模型 | 输入 | 输出 | 它的性质 |
|---|---|---|---|
| planner_pre | 稳定设定 + 权威状态 + 本轮输入 + 节奏/随机事件指令 | 固定 14 字段的 brief JSON | **契约生成器**（含 1 个窄工具） |
| story | 同一份稳定设定 + 权威状态 + brief 拼成的要求 | 中文正文 | **纯函数式文本生成器** |
| planner_post | 回合前状态 + 本轮输入 + brief + 本轮正文 | 固定结构的增量 Patch | **契约生成器** |

三者的输出结构都由程序模板固定，程序对每一层都做白名单校验。也就是说：**"agent 的多轮"在架构上由玩家承担**——玩家每一轮输入就是一次外部观察，模型不能自己决定"再来一轮"。

这正是"输入的定死 + 输出的定死"该有的样子：**它们的自由度在内容里，不在流程里。**

---

## 二、实测：规划模型并没有"想不完"

### 2.1 输出体量（29 个历史回合）

| 指标 | planner_pre 的 brief | planner_post 的 patch | 正文 |
|---|---|---|---|
| p50 | **1,301** 字符 | 2,696 字符 | 4,632 字符 |
| p90 | 1,942 | 6,216 | 8,628 |
| max | **2,156** | **15,889** | 13,000 |

- planner_pre 的输出**最大也只有 2,156 字符**，约为最长正文的 **16.6%**。"一轮装不下"完全不成立。
- planner_post 的 patch **最大 15,889 字符，超过了它所结算的正文本身**（122%）——这一层才是"输出偏胖"的地方。

### 2.2 提示词体量（当前实现，E2E mock 采集的真实请求）

| 阶段 | 消息数 | 提示词合计 |
|---|---|---|
| planner_pre | 3（system + 稳定上下文 + 权威状态/输入/契约模板） | 3,035 字符 |
| story | 3 | 3,111 字符 |
| planner_post | 2（system + 全部材料） | **5,816 字符** |

这是**最小状态**下的结构对照（真实存档会大得多），但结构关系已经清楚：**结算阶段的输入是三个里最重的**，而它的输出也是最胖的。

### 2.3 历史失败模式：全部是契约问题，不是容量问题

对早期长局审计（`test-runs/long-behavior-audit-v4-pro-analysis.md`，当时协议含已删除的 `canonCheck` / `uncertainties`）中的失败逐条归类：

| 历史失败 | 归类 | 当前的对应处理 |
|---|---|---|
| `characters`/`threads` 没有提交 | 契约未落地 | 现在整轮必提交并由测试固定 |
| 字段名混用 `from/to`、`source/target`、`characterId1/2` | **schema 不合规** | 模板只给 `fromId/toId`，非白名单关系直接丢弃并告警 |
| 15 轮没有一条 facts 进状态（多为字符串） | **schema 不合规** | `facts` 强制结构化 + 强制 `evidenceQuote`，字符串项直接丢弃 |
| 写后结算出现旧回合污染（报告了第 10 回合的冲突） | **上下文继承** | 结算改为独立调用、不继承写前会话，只喂本轮材料 |
| 越权输入未被记录 | 已废弃字段 | `canonCheck`/`uncertainties` 已移除 |

**一条都不是"想不完"，全都是"没按契约输出"或"吃错了上下文"。** 多轮规划解决不了这两类。

## 三、为什么"多轮"在无工具时收益很低

harness 里的 agent 之所以多轮有效，是因为每个中间产物**都能被外部验证**：写了个文件 → 读回来看看；跑了个命令 → 看退出码。**多轮的价值来自"观察中间结果"，而不是"多想几次"。**

如果给规划模型加多轮，它没有可观察的外部对象（我们已经决定不给它开放检索工具），于是多轮只能变成**模型和自己对话**——常见的三个退化：

1. **自我肯定**：第二轮倾向于确认第一轮的结论，而不是推翻它；
2. **指令漂移**：每多一轮，原始要求被稀释一点（这也是"提示词越长越不听话"的同一个机制）；
3. **成本翻倍**：规划已经调用两次，再多一轮就是 3 次；而规划的输出只占正文的 16%，**性价比极低**。

**结论**：多轮该用在"能被外部校验"的地方（工具循环），不该用在"纯推理复用"上。规划模型目前没有需要外部校验的中间产物——它需要的是**把自己的输出对一遍固定清单**。

## 四、真正能提升规划可靠性的两件事（都不需要多轮）

### 推荐 A：给 planner_post 加"确定性自检回显"，而不是加一轮推理

> **状态：第一步（度量）已实现。** `patchStats` 现在会随每回合记录，见本文第八节。是否要做回显本身，取决于这个数字在真实长局里有多大——**先量，再决定**，避免白加一个字段进协议。

现状：结算输出的 patch 占它自己的输入体量最大、输出也最胖（最大 15,889 字符），而它的失败代价最高（结算失败 → 整轮作废）。

做法（**不是多轮对话，而是同一次调用内的一次结构化自检**）：在输出模板末尾追加一个程序可校验的清单字段，例如：

```
"selfCheck": {
  "usedExistingIds": ["..."],   // 本轮用到的已存在 id
  "newIds": ["..."],            // 本轮新建的 id
  "factsWithEvidence": 0,       // 带 evidenceQuote 的 facts 条数
  "beatChangesWithEvidence": 0  // 带 evidenceQuote 的 beatChanges 条数
}
```

程序拿到后**交叉核对**（不是相信它）：
- `usedExistingIds` 是否真的存在于权威状态 → 捕捉"重造 ID"这个历史最痛的失败；
- `factsWithEvidence` 是否等于实际提交的 facts 条数（差值即"被丢弃的 facts"）→ 把静默丢弃变成可观察数字。

这类字段的价值在于**把校验变成确定的**：模型说"我用了这些 ID"，程序一比对就知道它是不是在编。这比让它"再想一轮"可靠得多，也不增加调用。

### 推荐 B：把"每轮节拍清单"做成可校验字段（来自上一份评估的推荐 A）

写前规划现在产出的 brief 只有约 1,300 字符、`hardConstraints` 中位 7 条，说明它能想清楚"这一轮要钉住什么"。缺的不是思考轮次，而是**把关键约束变成程序可检查的形状**：

- brief 里补 `beatsThisTurn`（1–3 条明确的节拍）与不得越过的场景边界；
- 写后结算回填"实际覆盖了哪些节拍"；
- 程序对比两者，超额就记录偏差（不重写正文），让后续规划少安排一步。

这条直接针对实测到的真实症状：**79% 的回合正文超过 2,500 字、6,000 字以上的回合里有 14% 出现被禁止的升华式收尾**。而这属于"约束没被校验"，不是"规划想不完"。

## 五、明确反对的做法

| 做法 | 反对理由 |
|---|---|
| 让 planner_pre 多轮"先想再想" | 输出仅 1.3 KB、无外部可观察对象，收益接近零，成本 ×1.5~2 |
| 让 planner_post 先出草稿、再出正式 patch | 相当于把一次调用变两次，且第二轮的输入里已经含有第一轮的错误结论；正确做法是**一次输出 + 确定性交叉核对** |
| 给规划模型开放更多工具来"辅助思考" | 已决定不开放；当前唯一的检索工具覆盖了真实需求（回查早期正文与设定） |
| 引入"规划器 + 评审器"双模型互相评审 | 评审器没有独立信息源，只能复述；反而把 2 次调用变 4 次。历史上真正有效的评审是**程序侧的白名单校验**，它已经在做 |

## 六、方法与局限

- **2.1 / 2.2 的体量数据可信**，但要注意两点：(a) 29 个历史回合用的是**旧版协议**（含已废弃的 `canonCheck`/`uncertainties`，且没有 `activeBeatIds`），因此**不能用它判断当前规划器的节拍行为**，只能用于体量参考；(b) 2.2 是最小状态下的结构对照，真实存档的提示词会显著更大。
- **2.3 的失败归类**来自历史审计文档的逐条复核，与当前代码的对应处理是逐项核对的。
- **没有真值**：归档产物里没有"哪些 patch 是错的"这一标注，因此无法直接统计"结算错误率 vs 输出体量"的相关性。要拿到这个数据，需要用真实 API Key 重跑一轮长局并人工标注——这是**唯一能把推荐 A 的收益量化的办法**。
- 若要判断当前规划器的 `activeBeatIds` 是否真的为空（旧产物里没有这个字段，无法判断），同样需要一次真实长局的产物。

---

## 七、一句话总结

**规划模型不需要多轮，它需要"被校验"。** 它当前是"某个 agent 的一部分"——这个定位是准确的：它的自由度应该体现在**内容判断**上（这一轮怎么写、要不要迁移路线），而不是体现在**流程自主**上（自己决定再来一轮、自己决定用什么工具）。把流程自由度收在程序手里、把内容自由度留给模型，正是这套双模型设计一直成立的原因。

## 八、实施记录：提交对账统计（`patchStats`）

### 做了什么

`commitTurnPatchV2` 新增可选的第四个参数 `stats`（不传则行为与之前完全一致）。传入时，程序会把**模型提交了多少条、真正落地多少条、被整条丢弃多少条**逐类别算出来：

```ts
PatchCategoryStatsV2 = { input, applied, blocked, malformed }
// characters / relationships / inventory / threads / facts 各一份
PatchStatsV2 = { ...五类, coercedEnums }
```

- `malformed` 专门统计**结构不全**（模型漏填必填字段，例如 `update` 没有 `id`、`create` 没有 `name`）；
- `blocked - malformed` 则是**字段齐全但被拒**（引用了不存在的 id、缺 `evidenceQuote`、自环关系等）。

**这两者必须分开**，因为修法完全不同：前者要改输出模板与指令，后者才需要 id 回显校验。

统计结果写进 `TurnRecordV2.patchStats`，随存档持久化；有丢弃时会额外发一条 `patch_items_blocked` 汇总警告。

### 界面上哪里看

游戏页「本轮模型活动」面板 → 展开「写后结算」阶段 → 顶部一行：

```
状态提交对账：接受 5/6 条 · 丢弃 1 条（其中结构不全 0 条） · 改写枚举 2 处
```

无丢弃无改写时显示「无丢弃、无改写」，用中性色；有问题时变琥珀色。

### 为什么这一步先做

在不知道"实际被拒比例"的情况下加 `selfCheck` 字段是盲目的：如果比例本来就很低，那就是白加一个协议字段和一段提示词。所以顺序是：

1. **先量**（本次完成）——纯程序侧，零额外调用；
2. 用真实 API Key 跑一轮长局，看 `blocked` 与 `malformed` 的实际大小；
3. 数字可观时，再加回显字段（届时 `usedExistingIds` 直接对应 `blocked - malformed` 那一类）。

### 验证

- 单测：`tests/patch.test.ts` 新增 4 条（干净提交零丢弃、丢弃计数与分类、枚举改写计数、不传 `stats` 时行为不变）；
- E2E：`scripts/e2e-mock-flow.mjs` 新增 2 条断言（统计存在且干净补丁零丢弃、随存档持久化）；
- 体积：30 回合 430.1 KB（此前 420 KB），距 5MB 约 329 回合（此前 337），无实质回归。

### 当前仍缺的一步

**没有真实 Key，所以现在的 `blocked` 数字全部来自 mock**。要拿到有意义的结论，需要配置真实 API 后跑一轮长局（`node scripts/e2e-storage-growth.mjs 30` 或 `scripts/test-story-flow.mjs`），然后看活动面板或导出的 `turnRecords[].patchStats`。这是唯一能把"要不要做回显"从推测变成决定的数据。
