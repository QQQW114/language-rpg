## 0. 一页速览

- **产品**：纯前端、双模型驱动的中文互动小说 / 文字 RPG（`言灵 · Language RPG` v0.4.0，已部署 GitHub Pages）。故事以"命运骨架"驱动：作者编写「大纲 = 幕 → 故事节」，程序保存权威状态，模型负责把玩家的自由路径接回预设命运。
- **每个回合 = 3 次独立模型调用**：`写前规划(planner_pre) → 故事正文(story) → 写后结算(planner_post) → 程序校验提交(patch.ts)`。规划模型兼任 pre/post，故事模型只写正文。
- **当前注入方式**：每回合把**完整大纲 JSON（所有幕、所有故事节）** + 出身 + 命中的世界书条目 + 权威状态注入提示词。
- **当前实测问题**：①「当前幕」是模型自报的自由文本，**程序零校验**（模型可跳幕/倒退/写不存在的幕）；② 79.3% 的回合正文超过 2,500 字，6,000 字以上回合有 14% 出现提示词明令禁止的「升华式收尾」；③ 随机事件只有"到期提醒 + 三档强度"，事件发生一次就失忆（无历史、无目的绑定、无后果回收）。
- **用户提案（待评估）**：允许自定义数量的故事幕；默认注入上一幕/当前幕/下一幕；当前阶段完成后自动注入新阶段的提示词；强化随机事件等系统以提高故事创作上限。
- **我方初步判断**：方向正确，但**必须先有"幕的运行时状态机"**（程序权威），否则"自动注入下一幕"会随模型自报的 currentActId 抖动；真正缺的是"幕的完成判定 + 幕级注入窗口 + 幕级写作契约"，不是"更多文本"。
- **要外部模型回答的核心问题**：幕完成怎么判定、三幕窗口各注入什么、幕级提示词由谁写、随机事件如何有目的/有记忆/能回收、以及如何避免把"自由路径"写成"固定章节播放器"。

## 1. 产品定位与不可违反的约束

> 以下摘自项目最高层设计文档 `docs/destiny-driven-story-core.md`（冲突时以该文档为准）。

### 1.1 一句话定位

> 这是一个**设定好核心命运与结局、但允许玩家自由改变抵达路径**的 AI 互动故事系统。玩家既是故事中的主角，也是共同作者。系统不负责把玩家锁在固定路线中，而是负责让世界书设定的核心人物、矛盾、成长与结局，能够穿过玩家造成的路线变化，以新的合理形式继续发生。
>
> `玩家行为改变路径 ≠ 玩家行为取消世界命运`

### 1.2 明确不是什么

- 不是纯开放世界模拟器；不是以胜负/数值/平衡为中心的传统 RPG；
- 不是严格照搬固定章节与固定事件顺序的小说播放器；
- 不是对玩家行为进行许可判断、发现"越权"就拒绝的跑团裁判；
- 不是依靠大量 Agent、规则引擎和程序限制替代模型文学判断的系统。

> **程序不做"剧情警察"**：除数据安全、格式校验和明确的世界硬规则外，不应为了阻止玩家改变路线而增加拦截、重试、截断或复杂状态机。

### 1.3 固定的是命运功能，不是固定路线

世界书可以预设：故事最终要抵达的结局；主角必须经历的核心成长；关键人物及其承担的命运作用；必须完成的主要矛盾、关系变化或认知转变；世界不可突破的硬规律。

但以下内容允许随玩家行为迁移或替换：发生地点；事件顺序；事件的表面形式；关键人物进入故事的方式；承担某个剧情功能的具体场景；抵达结局的时间与路线。

> 因此，系统要保存和推进的是"命运功能"，而不是机械复刻某一条剧本路径。

### 1.4 程序职责与克制边界

程序应负责：保存世界书/历史/摘要/结构化状态；提供可靠上下文；校验并提交写后 Patch；稳定 ID；防止格式错误与重复提交；保存叙事速度；以轻量机制触发随机事件提示；稳定注入长期目标。

程序**不应**负责：判断玩家是否"有权"改变剧情；因路线偏离拒绝整轮状态；通过复杂规则限制关系发展速度；替模型判断剧情是否文学上合理；为偶发理解错误不断增加兼容；用硬编码路线把故事拉回原场景。

> 核心原则：**程序维护数据可靠性，不替模型做文学判断。**

### 1.5 随机事件的产品定义（原文）

> 不恢复随机事件 Agent、复杂事件库或繁重调度系统。程序仅在若干随机回合向写前规划注入一条额外要求，并允许在本回合或下一回合自然兑现，避免为了完成指令而强塞事件。随机事件必须与当前故事相关，不能只是无意义装饰。

三档要求原文：

**严格相关**

```
---额外---
在本回合或下一回合自然插入一个与当前故事严格相关的随机事件。
事件应与当前人物、环境、关系或进行中的故事线程直接相关，不能成为脱离正文的一次性装饰。
```

**严格相关且推进情节**

```
---额外---
在本回合或下一回合自然插入一个与当前故事严格相关的随机事件。
该事件必须推进至少一条当前故事线程、人物关系或现实处境，不能只是无后续影响的插曲。
```

**严格相关且推进长期命运**

```
---额外---
在本回合或下一回合自然插入一个与当前故事严格相关的随机事件。
该事件必须推进长期目标或提高故事完成度，使当前自由路径获得新的命运汇合机会。
```

> 随机事件可以制造新的角色、环境与局部变化，但最终仍需服务故事完成度。随机不等于无方向。

### 1.6 四档叙事速度（原文摘要）

- **慢叙事**：细致到动作、感官、心理和短句对话；一轮只推进很小的时间节拍；适合关键对话、情绪变化、冲突现场和重要关系节点。
- **标准叙事**：默认；一轮完成一次主要行动或一个完整场景；在细节与推进速度之间保持平衡。
- **快叙事**：以事件发展为单位；可连续完成一组直接相关的行动；保留关键选择、结果和关系变化，略过重复过程。
- **时间跨越叙事**：允许跨越数天或更长时间；以概述和关键节点串联；必须保留影响命运、人物关系、任务和硬状态的关键事件；不应把尚未建立的长期变化无证据地写成既成事实。

### 1.7 后续实现验收原则（原文）

每次修改程序/提示词/前端时至少检查：是否尊重玩家作为共同作者的路线决定权；是否仍持续维护世界书设定的长期命运；路线变化后模型是否在寻找自然的命运汇合而非拒绝玩家；随机事件是否服务当前情节或长期完成度；叙事速度是否真正改变时间与镜头尺度；程序校验是否只保护数据而没有升级为剧情裁判；写后状态是否只记录正文真实发生的变化；关键人物和事件功能是否可迁移，而非被固定地点和固定顺序绑死。

## 2. 技术框架现状

### 2.1 栈与部署

- Vite 5 + React 18 + TypeScript 5 + Tailwind CSS 3 + Zustand 4；**无后端、无数据库**，全部状态在浏览器 localStorage。
- 存储键：`lrpg.v2`（存档/回合状态）、`lrpg.settings.v2`（模型设置）、`lrpg.content`（自定义故事/世界书/出身，persist version 3）。
- 已发布 v0.4.0，部署于 `https://qqqw114.github.io/language-rpg/`；GitHub Pages 项目页子路径已适配。
- 本机开发环境**没有真实 API Key**，全部自动化测试用 mock `fetch`；第 5 节的真实质量数据来自项目方此前导出的真实游玩产物。

### 2.2 回合链路与失败处理

```text
写前规划 planner_pre（可带 1 个检索工具，工具轮 1~6 次请求）
→ 故事正文 story（流式，纯文本）
→ 写后结算 planner_post（固定输出模板 JSON）
→ 程序 commitTurnPatchV2 校验后合并为权威状态
```

- 两个 CAS 守卫：`patch.baseRevision` 必须等于当前 `revision`；前端提交时再比对 revision/turn。
- 解析失败直接抛错，不静默提交空补丁；`finish_reason` 为 `length`/`content_filter` 同样抛错。
- **新增（本轮）**：`planner_post` 失败时抛 `TurnPostFailureV2`（携带已生成正文/写前简报/commitId/已完成两阶段调用），`runTurnSettlementV2()` 只重跑结算；游戏页显示「正文已生成 · 结算未完成」，可只重试结算。
- 规划模型唯一工具：`search_story_context`（查历史正文/人物/关系/事实/线程，返回带回合号与来源的证据；中文单字人名可检索）。故事模型与结算模型**没有工具**，也不继承规划会话。

### 2.3 模型设置（影响写作与成本）

- 故事模型 / 规划模型分开配置；温度：planner_pre 0.25、planner_post 0.1、story 来自设置。
- 逐阶段思考强度（low/high/max）；关闭思考时显式发送 `thinking:{type:'disabled'}`。
- 规划上下文软预算默认 16,000 tokens（只裁"近期正文窗口"，结构化状态/大纲/世界书始终完整注入）。
- 故事阶段的近期正文窗口固定最近 8 条消息。
- 工具轮上限默认 2（1~6）。
- 故事正文默认不发送 `max_tokens`（`storyMaxTokens` 未设置/为 0 时）；由供应商给足预算，实测 13,000 字回合可完整收尾。
- 前缀缓存结构：每个阶段都是「固定指令与输出模板 → 可变材料（状态/输入/正文）」。实测（最小存档）可复用前缀：planner_pre 44.3% · story 50.3% · planner_post 67.0%，三阶段合计 56.9%。真实存档固定块不变而可变块更大，因此真实比例更高，但**上限由"每回合必须重发的权威状态与近期正文"决定**，80% 不可达。

### 2.4 成本结构（真实三回合实测，DeepSeek 官方价）

| 项 | 数据 |
|---|---|
| 输入 | 51,632 tokens（缓存命中 27.3%） |
| 输出 | 43,694 tokens（是输入的 0.85 倍） |
| planner_post 占输出 | **57%**（它只做"把写好的正文翻成状态增量"） |
| planner_post 思考/可见 | **4.9×**；单次调用 36,906 字符思考 |
| 按官方价折算 | 输出占 **82%** 费用；缓存优化理论上限仅约 16% |
| 其它杠杆 | 时段差价 2 倍（避开北京时间工作日高峰）；模型档位差价 3.25 倍 |

### 2.5 存档体积

- 持久化剔除 `turnRecords[].calls[].input`（三阶段完整提示词留档，约 208 KB/回合，占整包 97%）。
- 实测（本轮）：25 回合 361.4 KB，距 5 MB 约 **331 回合**；纯正文+状态口径约 1,109 回合。

### 2.6 测试体系

- Patch/命运回归脚本、存档体积脚本、故事链路 dry-run 脚本均通过。

## 3. 故事内容格式规则（预设故事格式）

### 3.1 数据结构（TypeScript 接口，逐字段）

```ts
// 大纲 = 一部故事的命运骨架
interface StoryOutline {
  id: string;
  title: string;              // 必填，工坊输入上限 60
  synopsis: string;           // 必填：主角是谁、从什么变化开始、要经历怎样的成长、最终抵达什么状态
  acts: StoryAct[];           // 有顺序，至少 1 幕；幕数无上限（UI 可增删/上下移动）
  tone?: string;              // 题材、氛围、内容比例、明确要避免的方向
  worldBookIds?: string[];    // 默认挂载的世界书；启程页可再勾选覆盖
  coverEmoji?: string;        // 卡片装饰符号
}

// 幕 = 一个有顺序的命运阶段
interface StoryAct {
  id: string;                 // 程序自动生成/去重；作者不手填
  title: string;              // 必填，如「第二幕 · 成长」
  purpose: string;            // 必填：这一幕必须完成的叙事作用（不是"发生什么"，而是"要完成什么"）
  beats: StoryBeat[];         // 至少 1 个
}

// 故事节 = 必须经历的叙事功能（不是场景/事件，而是结果性功能）
interface StoryBeat {
  id: string;
  title: string;              // 必填
  purpose: string;            // 必填：必须实现的结果；不锁死地点与发生方式
}

// 世界书 = 可检索的长期设定
interface WorldBook { id: string; name: string; description?: string; entries: WorldBookEntry[]; }
interface WorldBookEntry {
  id: string;
  name: string;               // 必填，条目名
  keywords: string[];         // 命中任一关键词则激活；去重去空白
  content: string;            // 必填，注入正文
  priority?: number;          // 排序，大者先注入；允许区间 [-10000, 10000]
  alwaysActive?: boolean;     // 严格 true 才常驻注入
}

// 出身 = 开局载体
interface Background {
  id: string; name: string; description: string;  // 均必填
  traits: string[];
  startItems: string[];
  startScene: string;         // 必填：开局正文（作为第一条 assistant 消息）
  coverEmoji?: string;
}
```

补充：**Journey（存档）** 创建时把 outline/background/worldFacts 复制进存档；`state.destiny.beats` 把 outline 的幕/节**扁平化**为运行时故事节（保留 `beatId`，丢失所属幕的显式分组）：

```ts
destiny.beats = outline.acts.flatMap(act => act.beats.map(beat => ({
  beatId: beat.id,
  status: actIndex === 0 && beatIndex === 0 ? 'available' : 'pending',
  evidenceTurns: [],
  updatedAtTurn: 0,
})));
```

### 3.2 校验规则

**内容库导入/校验（`src/lib/contentLibrary.ts`）**

- 大纲必填：`title`、`synopsis`、至少 1 幕；每幕必填 `title`、`purpose`、至少 1 个故事节；每个故事节必填 `title`、`purpose`。
- 缺失 ID 时自动生成（`outline_*` / `act_*` / `beat_*` / `wb_*` / `wbe_*` / `bg_*`）；重复 ID 会静默换新。
- 字段清洗：所有文本 `trim`；空串→`undefined`（可选字段）；`keywords`/`worldBookIds`/`traits`/`startItems` 去重去空；`priority` 取整并夹到 `[-10000, 10000]`；`alwaysActive` 仅严格 `true` 生效。
- 导入包信封：`{ kind: 'language-rpg.content-library', version: 1, exportedAt, content: { outlines?, backgrounds?, worldBooks? } }`；版本不符直接拒绝；裸 bundle 也接受；逐项校验，单条失败不影响其它条。

**工坊保存前规范化（`src/v2/workshop/model.ts`）**

- 同 trim/去重规则；空 `tone`/`coverEmoji`/`description` 降级为 `undefined`。
- 校验分级（错误阻断保存 / 警告只提示）：标题/简介/幕标题/幕目的/故事节标题与目的为空 = 错误；无 `tone`、无关联世界书 = 警告；非常驻且无关键词的世界书条目 = 警告。

**工坊编辑能力（作者可做的全部事情）**

- 故事：标题、封面符号、简介、叙事基调；任意增删/上下移动幕；每幕增删故事节、增删故事；
- 世界书：名称/描述、条目名称/关键词/优先级/常驻开关/正文；
- 克隆内置《错位青春》为可编辑副本（所有 ID 换新，关联世界书一并克隆并重映射）；
- 导出单个故事/单本世界书，或完整内容库 JSON；导入 JSON。

### 3.3 内置预设《错位青春》（当前唯一验证范本，全文）

这是目前唯一经过真实长局验证的格式范本。作者完全可以自定义不同的幕数（UI 已支持任意幕数），但**幕/故事节的写法约定**以它为准：幕写"阶段方向与成长"，故事节写"必须完成的叙事功能/结果"，不写地点、不写固定顺序、不写玩家只能做什么。

### 3.4 启程与运行时绑定

- 启程页三步：选故事 → 选出身 → 设定（旅程名、随机事件开关与回合区间、勾选世界书，默认勾选大纲推荐的）。
- 世界书勾选后**扁平化**为 `save.worldFacts`（条目数组，失去"属于哪本书"的归属，但保留条目级 keywords/priority/alwaysActive）。
- 随机事件区间合法化：最小 1、最大 100；`min > max` 时以 min 为准；创建时预排 `nextTriggerTurn = min + rand(0..max-min)`。
- 两种模式：**执笔模式**（author，无限回合自由输入，结算强制 actions 为空）；**游历模式**（adventure，结算生成 2~4 个可选行动，仍可自由输入）。
- 输入视角（仅执笔模式）：玩家视角 / 导演视角（导演视角下玩家输入视为不可撤销的故事指令）。

## 4. 运行时：模型看到什么、程序维护什么

### 4.1 权威状态 `GameStateV2`（程序侧唯一真相）

- 基础：`revision / turn / phase / mode / narrativePace / history[] / summary / latestProgress / lastCommitId`
- 场景：`currentScene { id, name, description?, time?, weather? }`
- 人物：`characters[] { id, name, aliases[], role?, description?, status(active|absent|missing|dead|unknown), knownFacts[], firstSeenTurn, lastSeenTurn }`
- 关系：`relationships[] { id, fromId, toId, affinity(-100~100), label?, note?, updatedAtTurn }`
- 背包：`inventory[] { id, name, kind(item|ability|quest_item), description?, quantity, consumable, acquiredAtTurn, updatedAtTurn }`
- 线程：`storyThreads[] { id, title, kind(main|relationship|quest|hook), status(candidate|active|completed|failed|cancelled), progress?, currentStep?, involvedCharacterIds[], note?, updatedAtTurn }`
- 正史事实：`facts[] { id, subjectId, predicate, value, scope, stability(core|stable), confidence(explicit), keywords[], evidenceTurn, evidenceQuote?, createdAtTurn, updatedAtTurn }`；每回合最多写 10 条、总量上限 160（优先保留 core + 最近 stable）；`temporary` 不持久化。
- 命运：`destiny { completionEstimate(0-100), completionReason, currentActId, currentStage, currentPath, nextMilestone?, convergencePlan?, endingReached, endingReachedAtTurn?, beats[], updatedAtTurn }`
- 故事节运行时：`beats[] { beatId, status(pending|available|active|satisfied|weakened|reframed|superseded), currentPlan?, evidenceSummary?, evidenceTurns[], replacementBeatId?, updatedAtTurn }`
- 随机事件：`randomEvent { enabled, nextTriggerTurn, pending, intensity(related|progress|destiny), lastTriggeredTurn?, triggerIntervalMin, triggerIntervalMax, lastPlan?, lastNote? }`
- 选项：`availableActions[]`（adventure 模式最多 4 条）
- 留档：`turnRecords[]`（每回合的输入/正文/三阶段调用/usage/patchStats，最多 100 条；持久化时剔除 `calls[].input`）

系统提示词中的硬规则（摘要）：只结算正文真实发生的事；`satisfied` 必须有正文原句证据且实现 purpose；`superseded` 必须同时给证据与**真实存在的** `replacementBeatId`；已 `satisfied` 不得无理由回退；枚举只能使用模板英文取值，不得翻译/自造；`endingReached` 只有在完成度 100 且全部故事节 satisfied/superseded 时才真正生效；必须复用已有 ID；没有变化必须输出空数组。

### 4.5 故事节状态机与结局判定（程序侧）

- 7 状态：`pending`（未到条件）→ `available`（条件成熟）→ `active`（正在发生）→ 终态 `satisfied` / `superseded`；另有 `weakened` / `reframed`（非终态，表示已实现结果被削弱或需换实现方式）。
- 程序校验：`satisfied`/`superseded` 必须带 `evidenceQuote`；`superseded` 必须指向大纲中真实存在的节，否则降级为 `reframed` 并发警告；已 `satisfied` 回退到 pending/available/active 会被拒绝；回退到 weakened/reframed 需证据；`beatId` 必须存在于大纲。
- **结局判定**：`endingReached=true` **且** `completionEstimate >= 100` **且** 全部故事节都为 `satisfied`/`superseded` 时，程序才置 `destiny.endingReached = true`。注意：当前 `currentActId`/`currentStage` 是模型自报的自由文本，程序**只做 80 字符截断，不校验是否存在于大纲**；没有幕级完成度概念，只有整体完成度（模型估值）。
- 玩家可见（命运卡）：完成度 %、当前幕（显示 `currentStage` 自由文本）、当前路径、完成度说明（折叠）、故事节列表（默认只显示非 pending 的，勾选"故事推进详情"后显示全部 + 下一里程碑 + 收敛计划）；另有「故事脉动」卡片显示随机事件状态/安排/结果。

### 4.6 随机事件现状（调度机制）

- 启程页开关 + 触发区间（回合数，1~100）。
- 每回合程序计算 `due = enabled && (pending || turn >= nextTriggerTurn)`；到期时向 **planner_pre 和 story** 注入三档之一的事件指令（`related` / `progress` / `destiny`，取当前 `intensity`）。
- planner_pre 可返回 `randomEvent.planned/summary`（程序存 `lastPlan`）；planner_post 返回 `randomEvent.handled/note`（程序存 `lastNote`）。
- 程序调度：到期且 `handled=true` → 重排 `nextTriggerTurn = turn + rand(min..max)`，随机换一档 intensity，记录 `lastTriggeredTurn`；到期但未 handled → `pending=true`，`nextTriggerTurn = turn+1`（顺延到下一回合强制再提醒）；未到期 → 调度字段不变（但 note 仍记录）。
- 缺口：没有事件历史（只有 lastPlan/lastNote）、没有事件类型/目的绑定、没有"事件后果"追踪、没有与幕/线程的联动；强度由程序随机切换而非按剧情需要。

### 4.7 世界书注入规则（`selectWorldFacts`）

- `alwaysActive` 条目每回合必进；
- 其余只有关键词命中**当前输入或最近 6 条历史**时才进；
- 按 `priority` 降序、同级保持原序，上限 20 条；超限发活动流警告（被截断内容仍可用 `search_story_context` 检索）；
- 世界书/大纲/出身在提示词里是"稳定上下文"，其 JSON 字段顺序固定（缓存考虑）。

### 4.8 程序对 Patch 的校验（只保护数据，不替模型判断剧情）

- 人物 create 撞名/撞别名走合并；线程 create 缺 title 整条忽略（不覆盖）；关系自环/目标不存在丢弃；好感单回合夹 ±20、累计夹 ±100；库存 grant 严格照抄数量（0 表示不加、负数表示减少）；每回合事实 ≤10、总量 ≤160、core 不可覆盖、临时/推测/无证据丢弃；可选行动最多 4 条且不得空 label；`roundSummary`/`latestProgress` 空串保留旧值。
- 提交对账 `patchStats`：每回合记录"模型提交多少、接受多少、丢弃多少（结构不全 vs 引用不存在）、改写枚举多少处"，写入 `TurnRecordV2` 并在活动面板显示。

来源：项目方此前导出的 29 个真实回合（DeepSeek v4-pro），以及一次真实三回合成本实测。

### 5.1 正文规模（29 回合）

| 指标 | 实测 |
|---|---|
| 正文字数 | p50 **4,632** · p75 5,832 · p90 **8,628** · p99 13,000 · max 13,000 |

| > 6,000 字的回合 | 24% |

| 超长被截断（`finish_reason=length`） | **0 条** |

### 5.2 收尾问题

- 用五类"升华/收束"模式检测每回合最后 220 字：0–6,000 字档位 **0%**；**6,000 字以上档位 14%**；29 回合共命中 1 例（10,314 字的一轮，结尾是"这个影子的形状不属于曦宇。它属于曦雨，而且从今天开始，它有了同伴。"——正是提示词明令禁止的点明主旨/升华）。
- 该回合一轮从早上六点四十写到午饭，含 3 个时间推进词；另有 6 个回合含 2–3 个时间推进词。
- 结论（评估文档原文）：**"一轮写太多"的真实症状不是复读，而是"在一轮内部做出完整弧线，于是顺手给了个收束"**。

### 5.3 规划/结算输出体量

| 指标 | planner_pre brief | planner_post patch | 正文 |
|---|---|---|---|
| p50 | 1,301 字符 | 2,696 字符 | 4,632 字符 |
| p90 | 1,942 | 6,216 | 8,628 |
| max | 2,156 | **15,889**（超过它所结算的正文） | 13,000 |

- planner_pre 输出最大仅约最长正文的 16.6% → "一轮装不下"不成立。
- planner_post 输入最重、输出最胖、失败代价最高（结算失败 → 整轮作废，现已可续跑）。
- 历史失败模式全部是**契约问题**（字段名混用、字符串 facts、旧回合污染、schema 不合规），不是"想不完"；因此结论是"规划模型不需要多轮，它需要被校验"。

### 5.4 成本与缓存（见 2.4/2.3）

- 输出占 82% 费用；planner_post 占输出 57%；思考/可见 4.9×。
- 全部缓存优化的理论上限只有约 16%；已有结构修复让三阶段可复用前缀从约 25% 提升到 56.9%（最小存档）。

### 5.5 现有评估文档的建议（与本提案相关）

- 《要不要把一轮拆成多轮增量生成》：**不建议拆**（缓存失效、延迟翻倍、语气漂移）；真正该改的两处：**A. 把篇幅控制变成可校验的约束**（写前给"本轮节拍清单 beatsThisTurn + 不得越过的场景边界"，写后回填实际覆盖、超额记偏差但不重写正文）；**B. 回合续跑**（已完成）。
- 《规划模型是否需要多轮》：不需要多轮；推荐 A「给 planner_post 加确定性自检回显」（先量 patchStats 再决定）；推荐 B「每轮节拍清单做成可校验字段」（与 A 相同）。

## 6. 用户提出的扩展方向（原文 + 拆解）

### 6.1 用户原文

> "允许自定义数量的故事幕，默认注入上一幕，当前，下一幕，在完成当前阶段后自动注入新阶段的提示词，同时强化随机事件等系统来提高故事创作的上限。"

### 6.2 拆解成三个能力

**A. 幕窗口注入**
- 现状：每回合注入**完整大纲**（所有幕、所有节）。
- 提案：默认注入「上一幕 / 当前幕 / 下一幕」。
- 隐含收益：聚焦当前阶段、减少远景干扰、降低提示词占用；隐含风险：丢失远景伏笔与最终命运锚。
- 与缓存的关系：完整大纲目前是"稳定前缀"的一部分；按幕窗口注入后，**幕内稳定、幕切换时前缀失效一次**（约每幕一次，可接受，但必须保证幕内逐字节稳定）。

**B. 幕完成判定与自动推进**
- 现状：`currentActId`/`currentStage` 是模型自报自由文本，程序零校验；没有幕级完成概念。
- 提案：当前阶段完成后自动进入下一幕，并注入新阶段的提示词。
- 隐含需求：程序必须知道"当前是哪一幕、这一幕是否完成、下一幕是谁"；否则模型自报抖动会导致"自动注入"乱跳。

**C. 强化随机事件系统**
- 现状：到期提醒 + 三档强度 + lastPlan/lastNote；事件发生一次就失忆。
- 提案：强化以"提高故事创作上限"。
- 需要明确：强化的是频率？质量？与主线的耦合？后果回收？还是"事件即命运推进器"？

### 6.3 用户意图（我方理解）

提高"故事创作的上限"——即在一部长篇互动故事里，让**结构感（阶段推进）**与**意外性（事件质量）**同时更强，同时不牺牲自由路径与玩家共同作者地位。用户担心的是"框架限制了创作上限"，而不是"功能不够多"。

## 7. 我方初步判断与设计草案（请外部模型批判）

### 7.1 判断

1. **方向正确，但顺序关键**：应该先把「幕」变成**程序权威的运行时状态机**，再做窗口注入与自动推进；否则"自动注入下一幕"建立在模型自报的 `currentActId` 上，会抖动、跳幕、倒退（当前代码只截断 80 字符，不做存在性校验）。
2. **"自定义幕数量"其实已经支持**：工坊可任意增删/排序幕；缺的不是数量，而是运行时语义。
3. **幕是解决"提前收尾"的天然抓手**：当前模型在一轮内写完完整弧线并升华收尾（6,000 字以上档位 14%）。"本幕故事节未完成前不得写幕收束"是一条比现有 `stopBoundary` 更硬、更合法的叙事边界。
4. **随机事件的真正问题不是"不够随机"，而是"没有目的、没有记忆、没有后果"**：三档强度已经区分了"相关/推线程/推命运"，但事件本身不绑定任何服务对象，也没有历史可供后续回收。

### 7.2 草案（待批判）

**Step 0｜幕状态机（先做，纯程序）**
- `currentActId` 改为程序派生：第一个"仍有非终态故事节"的幕；若全部终态则进入结局判定。
- 校验模型提交的 `currentActId`：不存在/跳幕/倒退 → 拒绝或纠正 + warning（沿用项目"静默丢弃改为可观察"原则）。
- 幕进度 = 该幕故事节终态比；侧边栏显示「幕 2/5 · 本幕 3/4 节」。
- 只持久化少量元数据（`actEnteredTurn`、`completedActIds`），不复制第二份真相（避免与 beats 双写漂移）。

**Step 1｜工坊幕级字段（作者上限的直接来源）**
- 给 `StoryAct` 增加可选字段（名称待定）：`entryNote`（进入此幕的舞台/人物/关系背景交代）、`exitCondition`（人类可读的完成条件）、`stageBrief`（本幕写作要求，如"本幕只铺垫、不得解决核心矛盾"）。
- 程序只做"数据注入"，不生成文学内容；缺省时退化为现有行为（不逼作者填写）。

**Step 2｜注入窗口化（用户说的"上/当前/下"）**
- 建议五段式：永远注入世界书 + 剧情简介 + 最终命运锚（结局/收敛计划/下一里程碑）→ 上一幕压缩为 1–2 行因果摘要 → 当前幕全量（title/purpose/beats/entryNote/stageBrief）→ 下一幕一行 teaser（title + purpose 摘要）→ 后续幕只给标题或数量（"还有 2 幕未展开"）。
- 消息排列：稳定部分（system、世界书、最终命运锚、全大纲标题清单）在缓存前缀内；幕窗口块紧随其后（幕内稳定）；权威状态与输入在最后。

**Step 3｜幕推进协议**
- planner_post 提交幕推进提议（`targetActId` + `evidenceQuote` + `reason`）；程序 gate：当前幕故事节全部终态（satisfied/superseded）+ 目标幕存在 + 建议顺序不倒退；接受后注入下一幕的幕级字段作为【ACT_BRIEF】，并记录幕切换回合。
- planner_pre 每回合仍需输出当前幕的施工说明（复用现有 `currentAct` 字段），作者字段存在时作为高优先级约束。

**Step 4｜随机事件强化（轻量，不恢复事件库/事件 Agent）**
- ① 事件记忆：`randomEvent.history[]`（上限如 8 条：turn/摘要/强度/是否兑现/关联对象），持久化并注入，让伏笔可回收；
- ② 目的绑定：规划时要求事件绑定服务对象（某个 active 故事节 / 线程 / 关系 / 命运汇合），三档强度对应"相关/推线程/推命运"；结算回填是否兑现（只观察不强制）；
- ③ 幕边界大事件：幕切换是天然"大节拍"，新幕开幕可强制注入一次强事件（换舞台/新人物入场/关系转折），把随机调度挂到幕结构上；
- 不做：事件库、事件 Agent、复杂调度、给规划模型加工具。

**Step 5｜评估与验收**
- 用真实 Key 跑 20+ 回合 A/B：升华式收尾比例（目标：不高于基线）、单轮时间跨度、幕跨度、事件回收率、正文长度分布、成本与延迟；离线侧用 mock 断言结构（幕内前缀稳定、幕切换才变、幕状态机合法转移）。

### 7.3 我方识别的风险（请外部模型评估并补充）

1. **缓存前缀**：按幕窗口注入会让前缀在幕切换时失效一次；若 `currentActId` 抖动则每回合失效 → 所以必须程序权威。
2. **幕卡死**：现有故事节只有 `satisfied`/`superseded` 是终态；`reframed`/`weakened` 是非终态。若玩家路线让某节永远无法满足，幕可能永远无法推进；需要设计"幕级改道/合并/放弃"的合法出口（但不能放宽结局判定门槛）。
3. **剧透与伏笔**：只看上一幕/当前幕/下一幕，远处的伏笔与结局暗示可能丢失；需要保留"最终命运锚"（结局条件/核心矛盾）与后续幕的一行摘要。
4. **提示词膨胀**：幕级字段若写得太长，会挤占叙事约束，反而降低写作质量；需要长度预算。
5. **与产品约束冲突**：幕系统容易滑向"固定章节播放器"（产品明确禁止）。需要明确：幕是"命运阶段"，不是"剧情章节"；幕完成判定依据"故事节功能是否实现"，而不是"是否到了第 N 回合"。
6. **程序越权**：幕推进判定若由程序硬判，可能变成"剧情警察"；需要保持"程序 gate + 模型提供证据 + 允许改道"的分工。
7. **成本**：多注入幕信息会增加输入，但输入只占成本 18%；主要成本仍是输出（尤其 planner_post 思考）。幕系统若能减少长回合浪费，可能反而省钱，但需要实测。
8. **旧内容兼容**：旧故事没有幕级字段，需要退化模式；旧存档的 `currentActId` 可能是自由文本，需要迁移策略。

### 7.4 明确不做（我方立场）

- 不恢复事件库 / 随机事件 Agent / 复杂事件调度系统（产品文档明确禁止）。
- 不把故事回合拆成多轮增量生成（已有评估结论；缓存、延迟、语气漂移代价大于收益）。
- 不让程序生成文学内容或重写正文（程序只注入作者数据与校验状态）。
- 不用硬编码路线把故事拉回原场景（命运功能可迁移）。

### B. 四档叙事速度提示词原文（`paceInstruction`）

```
慢叙事：本轮只展开一个微小而连续的故事节拍，例如一次关键动作、短暂观察或一小段对话。细致呈现真正发生的变化，但不要用重复心理、感官或环境描写人为拉长。停在最早的自然回应点，把动作结果、他人反应或下一步选择留给玩家继续参与。节奏不是硬字数限制。

标准叙事：本轮聚焦玩家的一次主要行动或一个连续场景，只推进到该行动产生明确反馈、玩家可以再次回应的位置。不要把反馈之后的余波、转场、下一场互动和后续决定一并写完；即使它们顺理成章，也应留给下一回合。不要写成包含完整事件链的独立短篇，节奏不是硬字数限制。

快叙事：本轮以事件发展为单位，可以推进一组直接相关的行动，概括次要过程并展开关键互动。速度指事件数量与故事时间跨度，不限制必要描写篇幅。

时间跨越叙事：本轮允许跨越数天或更久，概述重复日常，重点展开命运节点、关系变化与关键结果。字数由需要保留的关键节点决定。
```

### C. 随机事件指令原文（`randomEventInstruction`，程序当前实现）

```
related  ：---额外---：在本回合或下回合自然插入一个与当前故事严格相关的随机事件。事件必须联系当前角色、环境、关系或active/available故事节，不能是无关装饰。
progress ：---额外---：在本回合或下回合自然插入一个与当前故事严格相关的随机事件。该事件必须推进active故事节，或为available故事节创造自然条件，不能只是一次性插曲。
destiny  ：---额外---：在本回合或下回合自然插入一个与当前故事严格相关的随机事件。该事件必须推进核心故事节、为reframed故事节找到新实现形式，或推进最终结尾条件。
（三档都追加：随机事件同样服从当前叙事速度：慢叙事或标准叙事可以只让事件自然出现或推进一小步，不必在本回合解决完整事件。）
```

### D. 写前规划系统提示词原文（`buildPlannerPreSystem`）

```
你是互动小说的写前规划 Agent，只做本回合写作约束，不扮演角色，不续写正文，只输出严格 JSON（json object）。
优先级：玩家明确行动 > worldFacts硬设定 > canonicalFacts旅程正史 > 当前程序状态 > 近期正文 > 合理补全。
玩家也是共同作者。不要把偏离当前路线的行动视为越权，不要机械拒绝；根据世界规律写出其合理结果，并允许玩家真正改变地点、身份、关系和抵达路径。
长期大纲描述的是必须逐步抵达的命运、人物成长和设定结局，不是固定路线。玩家改变路线后，规划关键角色、矛盾和事件功能如何自然迁移到新环境，使自由路径最终重新汇合到预设命运。
偏离只影响抵达速度和路径，不取消长期命运。不要为了拉回大纲而立刻强塞关键角色；本轮只安排自然、可信的一步。
允许补全资料空白，但只补本回合必要内容。不得预先决定玩家下一步，不得把“考虑、可能、打算”写成已完成决定。
叙事速度约束的是单回合覆盖的故事时间、主要动作和场景数量，不是要求凑够篇幅。慢叙事与标准叙事应选择最早且有意义的玩家可介入节点，给后续回合保留反应、对话和后果；不得把一次输入扩展成自带开端、发展、结尾的完整短篇。
stopBoundary必须是本轮正文最后一个允许发生的动作；不得把边界后的动作、事后反应、下一地点或后续安排写入writingBrief。
```

### E. 写后结算系统提示词原文（`buildPlannerPostSystem`，摘要）

```
你是互动小说的写后审计与状态提交 Agent。你不是作者，不续写故事，不规划下一幕，不扮演角色。只依据本次提供的CURRENT_TURN_INPUT与CURRENT_STORY结算本回合，只输出严格 JSON（json object）。
摘要、进度和Patch必须是CURRENT_STORY已经明确发生的内容；“准备、考虑、计划、可能”不能记为已完成行动。
每轮必须更新destiny，但只更新实际变化的故事节。故事完成度是当前全部事件与人物状态距离预设结尾的综合估值，可上升也可下降，不是累计积分。
故事节状态含义：pending未到条件；available条件成熟；active正在发生；satisfied核心功能已由正文满足；weakened已满足结果被后续削弱；reframed因路线变化需换实现方式；superseded已由等价故事节承担。
satisfied不是“提到过标题”或“计划过”的标记，只有当CURRENT_STORY实际实现了该故事节的purpose（叙事功能），并能用正文原句证明时才可使用。……已satisfied的故事节不得无理由回退……
玩家改变路线时优先reframed并更新currentPlan，不删除命运功能。不要强行拉回旧地点。
若CURRENT_WRITE_PLAN中的randomEvent.planned为true，只有CURRENT_STORY已经实际发生了对应安排的事件时randomEvent.handled才为true……
必须复用权威状态中已有ID。新对象ID使用稳定、简短、语义化的小写ASCII ID；同一对象后续永远复用该ID。
……枚举字段只能使用输出模板中列出的英文取值，不得翻译、不得自造同义词……
故事节的superseded必须同时给出evidenceQuote与replacementBeatId（且该id必须是已存在的故事节），否则整条变更被丢弃。
endingReached只在完成度达到100且全部故事节都已satisfied或superseded时才会真正生效……
```
