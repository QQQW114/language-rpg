# 评估：要不要把"一轮"拆成多轮增量生成

> 缘起：DSH 这类 harness 里的 agent 会把一个任务拆成多轮、一点点写文件。于是提出一个设想——`language-rpg` 的故事回合是否也该这样，避免"把所有任务积压在紧张的一轮调用里"。
>
> **结论：不建议。** 理由不是"做不到"，而是**实测数据显示假设中的症状基本没有出现**，而切分会引入三个新的真实退化（缓存失效导致成本翻倍、延迟翻倍、语气漂移）。本文给出全部证据、被证伪的假设，以及真正该改的两处。

---

## 一、先澄清架构：这一轮其实已经是多轮

一个游戏回合已经是 **3 次独立模型调用**，每次都有完整上下文、都能单独失败与重试：

```
planner_pre（可多轮：工具循环内 1~6 次请求） → story（流式正文） → planner_post
```

`llmClient` 里**已经实现了 agent 式多轮循环**（工具调用 → 结果回灌 → 再请求、轮数上限、末轮禁用工具），只是目前只有规划阶段用它。

所以"多轮"在架构上不缺零件，缺的是"把**正文本身**拆成多轮增量写入"。本文评估的正是后者。

---

## 二、实测证据（29 个真实回合）

数据来源：`test-runs/` 下三份真实 V2 产物——`long-behavior-audit-v4-pro.json`（15 回合）、`destiny-pace-10-v4-pro.json`（10 回合）、`misplaced-youth-v4-pro-full.json`（4 回合）。

### 2.1 假设一："一轮要做的事太多" —— **部分成立**

| 指标 | 实测 |
|---|---|
| 正文字数 | p50 **4,632** · p75 5,832 · p90 **8,628** · p99 13,000 · max **13,000** |
| > 2,500 字的回合 | **79.3%** |
| > 6,000 字的回合 | 24% |

一轮的正文规模远大于设计预期（"一次主要行动或一个场景"）。**这一条成立**：模型确实经常在一轮里写完一整个上午甚至一整天。

### 2.2 假设二："长回合会复读/退化" —— **不成立**

| 指标 | 实测 |
|---|---|
| 后半段与前文三元组重叠率 | 中位 **8.9%** · 最高 14.6% |
| 复读率 > 30% 的回合 | **0%** |

按长度分桶（检验"越长越容易复读"）：

| 正文字数区间 | 回合数 | 平均复读率 |
|---|---|---|
| 1,000–1,500 | 3 | 2.5% |
| 1,500–2,500 | 2 | 2.6% |
| 2,500 以上 | 23 | 8.4% |

长回合的复读率**确实更高**（8.4% vs 2.6%），但绝对水平很低，没有任何回合进入"明显复读"区间。**"写得长导致质量崩坏"没有数据支持。**

### 2.3 假设三："输出被长度限制卡住" —— **不成立**

- 三个文件里 `finish_reason=length` 类错误 **0 条**；
- 13,000 字那一回合完整收尾，没有截断。

`storyMaxTokens` 默认为 0（不发送限制），供应商侧给了足够预算。**"积压"不是被输出上限逼出来的。**

### 2.4 假设四："模型在一轮里草草收尾" —— **轻微成立，且与长度相关**

用五类"升华/收束"模式检测每个回合最后 220 字（主题升华、总结性断言、时间跳跃收束、悬置式预告、章节式收束）：

| 正文字数区间 | 有升华式结尾的比例 |
|---|---|
| 0–1,500 | 0% |
| 1,500–3,000 | 0% |
| 3,000–6,000 | **0%** |
| 6,000 以上 | **14%** |

29 回合中命中 1 例（`destiny-pace-10` 第 5 回合，10,314 字），结尾是：

> 「这个影子的形状不属于曦宇。它属于曦雨，而且从今天开始，它有了同伴。」

这正是提示词明令禁止的"点明主旨、升华"。**它出现在最长的那一档**，说明"一轮写太多"的真实症状不是复读，而是**在一轮内部做出完整弧线，于是顺手给了个收束**。

该回合还含 3 个时间推进词（一轮从早上六点四十写到午饭），另有 6 个回合含 2–3 个时间推进词。

### 2.5 检测方法的局限（如实说明）

- 模式匹配只能抓**显式**收尾表达，3% 是**下限**；"影子/同伴"这类意象式升华换个词就漏掉。
- 三元组重叠率只衡量**字面**重复，抓不到"同义复述同一件事"。
- 29 个回合、多数来自同一条预设，样本量不足以做统计推断，只能看趋势。

## 三、为什么"切分生成"不是正解

即使 2.1 与 2.4 成立，把正文拆成多次调用会引入三个**新的真实退化**，且都打在最贵的地方：

| 代价 | 机制 | 严重程度 |
|---|---|---|
| **成本 ×2~3** | 现在的消息顺序（稳定字段在前、每回合必变的 `turn/revision/summary/progress` 与 recent 放最后）是**特意为命中 prompt cache 排的**。拆成多次调用后前缀都变了，**缓存基本失效**——而缓存命中是当前省输入计费的主要手段（面板上的"缓存命中 token"就是它）。 | 高 |
| **延迟 ×2~3** | 玩家在等正文。agent 可以等几分钟，因为它"在做正事"；互动小说的等待本身就是体验损失。 | 高 |
| **语气漂移** | 分段独立生成最容易出现叙述语气断裂，而这恰恰是读者最先察觉的退化——比复读更伤阅读体验。 | 中高 |
| **收束更难控制** | 每段都可能自己"想收尾"，要防住就得给每段加边界校验与修复重试，复杂度迅速上升（完整多轮方案是 300+ 行改动 + 一次协议变更）。 | 中 |

**核心判断**：agent 能多轮，是因为每一步都有**即时、客观、可验证**的效果（文件写出了、命令输出对了），且中间产物**不需要**呈现给用户。故事正文两条都不满足：中间产物必须连贯，完成判据是主观的。**可移植的是"失败恢复"，不是"把生成切碎"。**

## 四、真正该改的两处（按性价比）

### 推荐 A：把篇幅控制变成**可校验的约束**，而不是靠提示词自觉

现状：`stopBoundary` 只是一句要求，没有任何校验；`writingBrief` 也没告诉模型"这一轮最多走到哪个人物/场景边界"。于是 79% 的回合超过 2,500 字、部分跨越一整天。

最小改动（不改链路结构、不增加调用）：

1. 写前规划在 brief 里补一个明确的**本轮节拍清单**（`beatsThisTurn`，1–3 条）与"不得越过"的场景边界；
2. 写后结算**回填校验**：本轮实际覆盖的节拍是否超出清单。超出时不重写正文（代价太大），而是在 `destiny` 里如实记录"本轮超额完成了第 N 个节拍"，让后续规划少安排一步；
3. 活动面板暴露这个偏差，便于长期观察。

这条把"模型自觉"换成"程序可观察的偏差记录"。

### 推荐 B：回合续跑（失败恢复）

一轮正文写完却因为 `planner_post` 失败而全部作废，是当前最直接的浪费。做法：

- `runTurnV2` 在结算阶段抛错时返回 partial（带 `story` / `brief` / `commitId`）；
- 前端显示"正文已生成、结算未完成"，提供"仅重试结算"；
- 已生成的正文保留，重试只重跑结算（成本从"整轮"降到"一次结算调用"）。

**这条才是"多轮"思想的正确落点：把轮次用在可恢复上，而不是用在切分上。**

### 可作为实验（不建议直接常开）：两段式生成

如果将来仍想验证"拆开写是否更好读"，最小可信实验：

1. 规划模型输出 `storyBudget: single | two-shot`（由它判断本轮内容量）；
2. `two-shot` 时故事阶段两次调用：第一次写前半并留明确的未完成标记，第二次带前半原文续写，**两次共用同一条前缀**（把可变部分放最后，尽量保住缓存）；
3. 结算仍只一次，看到拼接后的完整正文；
4. 验收口径：同一输入、同一模型跑 20 轮 A/B，比较①升华式结尾比例 ②后半段复读率 ③单轮时间跨度 ④字数分布。**先出数据再决定常开。**

---

## 五、验收口径（若将来改动）

- 升华式结尾比例（尾 220 字模式检测）**不得高于**基线（29 回合中 1 例，集中在 6,000 字以上档位）；
- 复读率（后半段三元组重叠）**不得高于**当前 p90（14.6%）；
- 单轮时间跨度：含 ≥2 个时间推进词的回合比例应随节奏档位可解释；
- 成本与延迟：以 `turnRecords[].calls[].usage` 与面板耗时为口径，不得出现无解释的翻倍；
- 回归：`npm test`、`npm run test:e2e`、`npm run test:patch` 全绿。

```bash
node test-runs/eval-multiround-evidence.mjs
```

若要长期复用，应移入 `scripts/` 并接入 npm scripts。
