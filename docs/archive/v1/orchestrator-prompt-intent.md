# 回合司辰提示词重构意图记录

> 记录时间：2026-05-11  
> 用途：给后续继续精修提示词的模型 / 维护者读取，避免上下文丢失。  
> 当前状态：用户正在主改提示词；维护侧只按明确要求协作，不主动大范围改写。

## 总体方向

当前项目正在从“多模型辅助文字 RPG”进一步转向“纯前端故事 Agent”。核心目标是让故事像一部逻辑稳定的小说：

- 大纲、世界书、主弧、已确认正文是上级依据。
- 故事不是每回合自由发挥，而是由调度层判断是否需要规划层介入。
- 规划层负责补足人物、场景、事件、阶段、设定等信息。
- 故事写手只负责执行已经整理好的叙事包与上下文，不承担全部规划职责。
- 工具调用与司书库会成为降低上下文成本、按需查证信息的核心方式。

## 提示词协作约定

- 用户正在精修 prompt，维护模型不要擅自重写整段提示词。
- 需要修改时，只改用户明确指定的部分。
- 不要在面向模型的提示词里写“未来 / 如果未来”这类工程规划式说法。
- 提示词应该描述“当前可用能力”和“当前任务边界”，不要让模型看见实现计划或开发 TODO。
- 真正的工具功能介绍应放在 `tools[].function.description` / `parameters.properties.*.description`。
- system prompt 只保留：
  - 模型身份；
  - 任务边界；
  - 工具使用原则；
  - 调度/输出规则。

## 回合司辰的定位

`authorOrchestrator` / 回合司辰是故事 Agent 的调度层，不是故事作者。

它的职责：

- 在新回合开始前运行。
- 初步判断当前回合类型。
- 判断旧计划、主弧阶段、事件弧、规划层输出是否过期。
- 判断是否需要调用某个专门模型。
- 决定模型调用顺序。
- 必要时使用工具查证资料。

它不应承担：

- 写故事正文；
- 详细规划具体剧情；
- 替代 `stageJudge` 做最终玩家意图 / 阶段判断；
- 生成长期记忆候选；
- 生成世界书内容；
- 修改能力、NPC、场景或阶段状态。

## 司辰应该理解的模型分类

这套分类主要是给司辰看的，不是完整项目文档。司辰只需要知道自己调度判断中会用到的角色。

### 核心调度

- `authorOrchestrator`：司辰自身。负责调度和信息收集。
- `story`：故事写手。它是最终服务对象，不应在 `calls` 中显式输出。

### 前置判断 / 设定模型

- `outlineMapper`：把当前剧情映射到原始大纲和主弧，指出阶段、偏离风险和桥接需求。
- `stageJudge`：判断玩家意图、玩家节奏、阶段是否过期、beat 是否完成或需要切换。
- `settingGuard`：检查世界书、身份、能力、规则、已确认设定是否被冲突或改写。

### 规划层模型

- `characterPlanner`：分析关键人物是否应出场、人物关系如何推进、角色知情范围和动机。
- `scenePlanner`：分析地点、时间、天气、空间资源、场景合理性与互动点。
- `eventPlanner`：分析当前小事件目标、生命周期、完成 / 失败 / 放弃 / 延后标准和写作边界。
- `director`：整合大纲、主弧、阶段判断、人物、场景和事件规划，生成给故事写手的 `writingBrief`。

### 后处理 / 维护模型

- `logicCheck`：故事后审校时间线、设定、人物、能力、场景和大纲一致性。
- `memory`：整理需要长期保持的事实、承诺、外观细节、关系变化、能力和场景记忆。
- `summary`：压缩较长历史。通常由代码兜底触发；司辰只在阶段收束、资料混乱或历史强影响当前判断时建议调用。

不应让司辰重点理解或输出：

- `masterArc`：属于旅程开局 / 主弧缺失时的上游骨架生成，不是普通回合司辰调度目标。
- `review`：旅程结束评价，不参与普通回合。
- `decision / decisionTracking`：故事后的状态落地链路，不由司辰在 `calls` 中调度。
- `randomEvent`：旧动态随机事件系统已不作为司辰主链路角色。

## stageJudge 与司辰的边界

司辰只做阶段相关的初筛：

- 当前回合是否可能涉及玩家意图变化；
- 当前 beat 是否可能完成；
- 当前阶段是否可能切换；
- 玩家节奏是否可能影响推进粒度。

若这些判断不确定，应安排 `stageJudge`，并以 `stageJudge` 的结果作为后续调度依据。  
司辰不应自己替代 `stageJudge` 输出最终玩家节奏或阶段结论。

## 工具使用意图

司辰可以使用工具，但工具调用应当“带问题”：

- 查询角色时，明确问：这个角色是否已有档案？与当前事件有什么关系？是否应出场？
- 查询场景时，明确问：当前地点是否支持这个行动？时间天气是否应影响行动？
- 查询事件时，明确问：当前事件是否完成、失败、延后，还是仍在推进？
- 查询大纲 / 开局 / 回合卷宗时，明确问：当前输入是否触及关键起因、能力获得、身份秘密或大纲节点？

工具使用原则：

- 按需、少量、优先读取最可能改变调度判断的信息。
- 不要因为有工具就查全量。
- 工具真实能力以 `tools[].function.description` 为准。
- 工具结果只用于调度判断，不写进正文，不伪装成模型自己的记忆。

## planningMode 方向

### light

玩家只是：

- 观察当前场景；
- 追问一句话；
- 做当前事件内的小动作；
- 继续当前对话；
- 当前 `writingBrief` / 事件边界仍然有效。

通常：

- 不调用 `director`；
- 阶段不确定时只安排 `stageJudge`；
- 否则可以不调用规划层。

### focused

玩家行动触及：

- 人物关系推进；
- 地点切换；
- 线索触碰；
- 事件转折；
- 当前目标改变。

通常：

- 先安排 `stageJudge` 或相关工具查证；
- 再按需要安排 `characterPlanner` / `scenePlanner` / `eventPlanner`；
- 必要时由 `director` 汇总。

### full

适用于：

- 回溯关键起因；
- 触及身份 / 能力硬设定；
- 阶段可能切换；
- 事件完成 / 失败结算复杂；
- 旧计划明显失效；
- 最近正文可能偏离大纲、世界书或角色档案。

通常：

- 先查证大纲 / 开局 / 旧回合；
- 安排 `outlineMapper` / `stageJudge` / `settingGuard`；
- 再按相关性安排规划层；
- 最后由 `director` 汇总。

## 计划过期信号

司辰需要更明确地判断“旧计划是否还能用”。过期信号包括：

- 下一回合已超出导演计划覆盖范围。
- 当前事件目标已经完成、失败、被放弃或被玩家绕开。
- 玩家行动改变地点、关键人物关系、身份 / 能力规则、事件目标或阶段目标。
- 旧计划没有覆盖刚发生的新变化。
- `stageJudge` 判断阶段完成、玩家节奏显著变化，或当前 beat 已不适合继续。
- `settingGuard` / `logicCheck` 留下高风险问题，但旧计划没有处理。
- 最近故事与主弧、大纲、世界书或角色档案出现明显偏航。

## 大纲与世界书优先级

- 一切调度以故事大纲、世界书、主弧和已确认正文为上级依据。
- 但大纲不是每个小动作的硬性映射表。
- 玩家沉浸在当前小事件中时，不必每回合强行调用 `outlineMapper`。
- 只有大纲映射不清、桥接不足、回溯关键节点、阶段可能变化或计划过期时，才需要重做大纲相关判断。

## 随机事件系统状态

旧的 `randomEvent` / 动态随机事件系统暂不继续作为独立司辰调度目标。

当前意图：

- 不动旧代码主体，避免破坏现有功能。
- 在文档中标记旧方案已弃用。
- 在司辰提示词中移除 `randomEvent` 的介绍和输出模板。
- 事件能力后续应并入主链路：司辰 → 事件规划员 → 叙事导演 → 故事写手。

相关文档：

- `docs/author-mode-random-events-plan.md` 已标记为“已弃用（留档）”。

## 当前仍需后续继续打磨的点

- 各工具 `description` 是否足够清晰，尤其是司辰可用的读档、读大纲、读回合、读模型输出工具。
- `stageJudge` 与司辰的多轮协作方式：司辰初筛 → stageJudge 输出 → 司辰复判。
- `characterPlanner / scenePlanner / eventPlanner` 已改为司辰直属分析工具；需要继续补齐工具调用记录、司书库 planning artifact 自动保存、前端可视化。
- `director` 何时必须调用，何时可沿用旧 writingBrief。
- `summary / memory / logicCheck` 的触发条件是否还需要继续收窄，以控制成本。

## 司辰分析工具链待补齐事项

当前链路已经能让回合司辰通过 `run_character_analysis` / `run_scene_analysis` / `run_event_analysis` 调用 A 类分析模型，并把结果写入 `authorNarrative.characterPlan / scenePlan / eventPlan`，供叙事导演与故事写手消费。

仍需补齐三项：

1. **A 类工具调用记录落盘**
   - 每次司辰调用人物 / 场景 / 事件分析工具时，记录该子调用的 input、output、thinking、usage、trace。
   - 记录页应能看见这些子模型调用，而不只看见司辰最终 JSON。

2. **A 类结果自动写入司书库 planning 文件**
   - 在写入 `authorNarrative.*Plan` 的同时，自动写入：
     - `planning/latest/character-plan.json`
     - `planning/latest/scene-plan.json`
     - `planning/latest/event-plan.json`
     - `planning/rounds/N/character-plan.json`
     - `planning/rounds/N/scene-plan.json`
     - `planning/rounds/N/event-plan.json`
   - 这些文件属于 planning artifact，不等同于正史。

3. **司辰工具调用前端可视化**
   - 回合进行中显示类似：
     - `回合司辰`
     - `调用了人物分析：问题 xxx`
     - `调用了场景分析：问题 xxx`
     - `调用了事件分析：问题 xxx`
   - 本回合结束后折叠进记录页或回合记录，避免主界面长期堆叠。
